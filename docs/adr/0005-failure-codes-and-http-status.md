# Failure Codes estáveis e mapeamento de status HTTP

Toda rejeição de negócio persiste um Failure Code estável de uma lista fechada (`INSUFFICIENT_FUNDS`, `REVERSAL_INSUFFICIENT_FUNDS`, `WALLET_NOT_FOUND`, `WALLET_PLAYER_MISMATCH`, `CURRENCY_MISMATCH`, `REFERENCE_NOT_FOUND`, `REFERENCE_UNSUCCESSFUL`, `REFERENCE_MISMATCH`, `REFERENCE_AMOUNT_MISMATCH`, `REFERENCE_NOT_REVERSIBLE`, `REFERENCE_ALREADY_COMPENSATED`, mais `PERMANENT_ERROR` para `FAILED`), cada um classificado como corrigível ou definitivo e publicado com essa classe em `WagerTransactionRejected`. O status HTTP deriva do status persistido da Wager Transaction: `200` PROCESSED, `202` PENDING_REFERENCE, `422` REJECTED, `500` FAILED, com o mesmo corpo de resultado e o mesmo status no Replay. Erros que não geram registro usam o corpo `{code, message}`: `400` formato, `401` autenticação, `403` autorização, `404` inexistente ou de outro Provider, `409` conflito de idempotência ou Wallet duplicada, `503` falha transitória com `Retry-After`. Consideramos responder toda rejeição com `409` ou `400`, mas isso misturaria entradas que nada gravaram com resultados persistidos que o Provider precisa reconciliar. Com a separação, um 4xx com corpo de erro significa "nada foi gravado, corrija e reenvie" e o status do resultado significa "a operação existe e terminou assim", o que deixa Replay e retry seguros sem ler o corpo. `FAILED` responde `500` porque é uma falha do serviço registrada para auditoria.
